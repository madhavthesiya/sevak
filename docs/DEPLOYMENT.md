# Deploying SEVAK

The live demo runs on three free services:

| Part | Service | Notes |
|---|---|---|
| Database | Supabase (PostgreSQL) | One project; Flyway builds the schema and the demo data on the API's first start |
| API | Render web service, from [`render.yaml`](../render.yaml) | Docker, `api/Dockerfile`; deploys after CI passes |
| Web app | Vercel, from [`web/vercel.json`](../web/vercel.json) | Static build of `web/` |
| Keep-alive | A scheduled ping every 10 minutes | Render's free instances sleep after 15 minutes; the ping also keeps Supabase active |

Put the database and the API in the **same region**: one page load runs several queries, and each one crosses that distance.

## 1. Database: Supabase

1. Create a project. Choose a **specific** region rather than a general one. Under Security, turn off the **Data API** and **automatically expose new tables**, and leave **automatic RLS** off: the API connects directly, and migration V14 sets up row-level security itself.
2. In the SQL editor, check that the owner can bypass row-level security, which the jobs need:
   ```sql
   SELECT rolname, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user;
   ```
   One of the two must be `true` (on Supabase, `postgres` has `rolbypassrls = true`). The API refuses to start otherwise.
3. **Connect → Direct → Session pooler → JDBC.** Note the host and the project ref (in the user name `postgres.<ref>`). Use the **session** pooler: the direct connection is IPv6-only on the free plan, and Flyway can't work through the transaction pooler.

## 2. API: Render

1. **New → Blueprint**, choose this repository. Render reads `render.yaml` and asks for the values marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `SEVAK_DB_URL` | `jdbc:postgresql://<pooler-host>:5432/postgres?sslmode=require` |
   | `SEVAK_DB_USER` | `sevak_app.<ref>` |
   | `SEVAK_APP_DB_PASSWORD` | a new long random password, without a `'` (Flyway gives it to `sevak_app` on every start) |
   | `SEVAK_OWNER_DB_URL` | the same URL as `SEVAK_DB_URL` |
   | `SEVAK_OWNER_DB_USER` | `postgres.<ref>` |
   | `SEVAK_OWNER_DB_PASSWORD` | the Supabase database password |
   | `SEVAK_CORS_ORIGINS` | the web app's address, for example `https://<project>.vercel.app` (update it once Vercel gives the real one) |

   `SEVAK_JWT_SECRET` is generated by Render.
2. The first deploy builds the image, then Flyway creates the schema, the `sevak_app` role and the demo data. The log should show `Requests run as 'sevak_app' (login 'sevak_app'), under row-level security`.
3. Note the service's address, `https://<service>.onrender.com`.

## 3. Web app: Vercel

1. **Add New → Project**, import this repository, set **Root Directory** to `web`. `vercel.json` sets the build.
2. Add the environment variable `VITE_API_URL` = the Render address (no trailing slash), then deploy.
3. If the Vercel address differs from what you put in `SEVAK_CORS_ORIGINS`, update it in Render; Render redeploys.

## 4. Keep-alive

Create a scheduled job (for example on cron-job.org or UptimeRobot) that requests
`https://<service>.onrender.com/actuator/health/readiness` every 10 minutes, with failure notifications on. It keeps the API awake, keeps the database active, and doubles as an uptime monitor.

## 5. Smoke test

```bash
node scripts/smoke-test.mjs https://<service>.onrender.com https://<project>.vercel.app
```

It checks health, the three demo logins, public pages, a full booking (book, accept, start, complete, pay, review), the admin pages, 401/403/404, CORS and the web app's deep links. It creates one booking; the nightly demo reset removes it. The first run can take a few minutes if the API was asleep.

## Notes

- The API won't start if its database login, or the role its requests run as, could bypass row-level security, or if the tables' owner can't (see [ADR 0008](adr/0008-row-level-security.md)).
- With `SEVAK_APP_DB_PASSWORD` unset, the API leaves the role's login alone rather than falling back to a default.
- The demo data resets every night at 03:00 IST.
